# Elektrokube upgrade and repository audit — 2026-10-06

The proposed branches update the verified current releases while preserving the
existing cluster design. They also fix SSO policy revocation, disable destructive
Helm remediation for storage, add schema/authorization checks, and pin CI actions.
Nothing in this audit deployed to a cluster or changed repository access controls.

exceptions, cookies/JWTs, group authorization, network policies, and CI. The older

GitHub release metadata, official chart artifacts and primary documentation were
checked on the date above. A targeted full-history scan found no private-key PEM
headers, GitHub token patterns, or AWS access-key IDs in the four repositories.
This is a limited credential-pattern check, not a guarantee that history contains
no secrets. No live credentials, users, Kubernetes objects, or production logs were
accessed. Container filesystem/SBOM scanning and a penetration test were not performed.

## Findings and disposition

Priority means deployment impact, not a claimed CVSS score. High findings should
be addressed before production rollout. Conditional findings identify the needed
precondition rather than claiming a demonstrated compromise.

| ID | Priority | Finding and evidence | Disposition |
| --- | --- | --- | --- |
| GIT-01 | High | GitHub reports `protected: false` for all four `main` branches and an empty ruleset list. Every Flux GitRepository follows `main`; a permitted direct push can change cluster-admin infrastructure or remove an auth gate. | **Open:** require PRs, successful validation and appropriate review, restrict bypass/force-push, and protect workflow/auth files with CODEOWNERS. Repository policy was not changed without an agreed reviewer/bypass policy. |
| SSO-01 | High | `sso-foundation` had `prune: false`. Deleting an allow policy from Git could leave it active. There was no namespace-wide deny baseline if the final service policy was removed manually. | **Fixed in SSO branch:** enable pruning, retain both namespaces explicitly, add default-deny ingress and regression checks. Validate the real Cilium datapath before merge. |
| SSO-02 | High | OAuth2 Proxy v7.15.4 precedes v7.15.5 security fixes, including path interpretation, forwarded client-IP trust and callback logging. | **Updated.** The shipped setup has no skip-auth-path or trusted-IP exemption, so those particular bypasses are not asserted exploitable here. Callback logging still motivates the patch. |
| STO-01 | High | Storage HelmReleases used remediation retries, allowing uninstall on failed installation and rollback on failed upgrade. These actions can remove a chart-generated secret or cross a state migration. Longhorn explicitly does not support downgrade after a successful upgrade. | **Fixed:** all three storage releases use `RetryOnFailure`. Failed transitions stay visible and need diagnosis; no automatic destructive recovery. |
| REC-01 | High | Authentik has one PostgreSQL instance on a one-replica `longhorn-cnpg` volume; Garage also has one instance/replica; backup targets and scheduled database backups are absent. | **Open:** create off-cluster backups, secure the SSO secrets and CA key, and demonstrate restore. Retained Kubernetes resources and same-cluster Garage are not independent disaster recovery. |
| IAM-01 | High | The blueprint uses the default authentication flow; the repository does not enforce administrator MFA. `cluster-admins` intentionally grants Authentik superuser rights and every registered service. | **Open:** verify/enforce MFA and least-privilege role assignments in the actual directory, test recovery, and rotate the bootstrap credential. Live user/flow state was not audited. |
| VAL-01 | Medium | Cilium/Flux had no CI workflow. SSO's manifest job only rendered YAML and did not render charts or check CRD schemas. | **Fixed:** foundation chart/schema validation and SSO chart/schema/security checks added. Existing real Heimdall/OAuth2 Proxy tests retained. |
| NET-01 | Medium | SSO DNS binds each node's host IP on TCP/UDP 53 and recursively forwards external queries. Host-network traffic is not protected by the pod default-deny policy. | **Open:** restrict DNS to intended LAN/VPN CIDRs at the host/router, confirm no public forwarding, and choose approved upstream resolvers. No LAN CIDR was invented. |
| NET-02 | Medium | Heimdall's gRPC and identity lookup use plaintext inside the cluster; Cilium node/host identities are allowed for ext_authz. No transport-encryption configuration is present. | **Open:** establish the trusted-node/network boundary; add tested Cilium encryption or backend TLS/mTLS if node-to-node traffic must be confidential. These flags were not blindly removed, which would break startup. |
| AV-01 | Medium | `API_IP` is the original first node; SSO DNS and OAuth2 Proxy's host alias depend on it. Authentik, authorizer, proxy and storage run single replicas. | **Open:** design a stable API/Gateway VIP and replicated state before promising HA. Extra control-plane nodes alone do not remove the first-node dependency. |
| IAM-02 | Medium | Rendered Authentik server/worker and secret-generator containers do not explicitly drop capabilities, deny privilege escalation, or set seccomp. Authentik correctly has no mounted API token; the generator must have one. | **Open:** test upstream-compatible pod hardening. Do not impose a read-only filesystem or UID without testing image startup and writable paths. |
| STO-02 | Medium | All StorageClasses use `reclaimPolicy: Delete`. Namespace/Cluster prune exclusions do not prevent an intentional PVC deletion from removing storage. | **Open:** choose retained classes for critical data if required; changing a class does not retroactively change existing PV reclaim policies. |
| OPS-01 | Medium | Bootstrap refuses changed saved configuration/node identity. Changing pins in Git does not upgrade already provisioned k3s nodes, and new enrollment reads the saved first-node pin. | **Documented:** perform a rolling k3s maintenance procedure and reconcile saved state afterward; do not delete the safety records to force reruns. |
| OPS-02 | Medium | Cilium handoff deliberately treats Git as authoritative and permits an upgrade or downgrade from the live Helm release. Previous README text falsely promised a matching-version/values preflight. | **Documentation fixed.** Version-transition enforcement remains an operator responsibility; read the actual live version and supported path before first adoption. |
| SUP-01 | Medium | Several images/charts use version tags rather than immutable digests; bootstrap checksums downloaded from the same publisher do not independently prove publisher identity. | CI action refs and validation binaries are pinned. **Remaining:** consider OCI digest/signature verification and a reviewed update process. Current chart-owned Cilium/Hubble digests are retained. |
| OBS-01 | Medium | No installed monitoring/alerting stack or external availability/expiry checks are defined here. | **Open:** monitor Flux failures, SSO denial/error rates, certificate expiry, PostgreSQL/Longhorn health and restore freshness. |

Other reviewed boundaries: k3s secrets encryption is enabled; node/root passwords
are transported through process memory/FDs rather than command-line arguments;
SSH host keys are explicitly pinned; a separate key-only connection is verified
before transactional SSH hardening; suspended or conflicting Flux ownership is
rejected; generated SSO secrets use `IfNotPresent` and prune exclusions. None of
these controls replaces physical host, live RBAC or network testing.

For the detailed SSO trust boundaries, retained risks and acceptance matrix, read
`elektrokube-sso/docs/audit-2026-10-06.md` on the corresponding change branch.

## Rollout order and recovery

1. Read the four PRs together. Establish branch controls and backups before merging
   into an automatically reconciled source. Confirm the cluster's actual versions,
   Git revisions, reconciler health, volume health and available capacity.
2. Reconcile the Cilium/Flux repository first. It updates Flux and Gateway API,
   preserving Cilium 1.20.2. Require every child to be Ready at the new revision,
   and test connectivity and the Gateway before moving on.
3. Upgrade storage from a healthy Longhorn 1.12.x installation. Follow the
   [Longhorn upgrade procedure](https://longhorn.io/docs/1.13.0/deploy/upgrade/),
   including V1 engine upgrades after the manager. Older minor versions need
   intermediate upgrades. Do not Git-revert Longhorn to downgrade migrated state.
4. Reconcile SSO during a maintenance window. Verify its new deny policy allows
   only required traffic; keep console/cluster-admin recovery access. Run the
   SSO acceptance matrix before closing the window. PostgreSQL stays on 17.11.
5. Merge bootstrap defaults for fresh installations. Existing nodes require the
   [k3s manual upgrade procedure](https://docs.k3s.io/upgrades/manual), servers
   followed by agents, preserving quorum and checking one node at a time. Back up
   etcd snapshots and the server token off-cluster. Update saved first-node/enrollment
   configuration and node identity versions only to match a completed, verified
   upgrade; never falsify them to bypass installation guards.

Suspend an affected reconciliation only as a deliberate incident action if a
transition fails; preserve its diagnostics and data. A stateless manifest revert
may be appropriate after compatibility review. Stateful software/CRD downgrades
require upstream-supported recovery or restoring a tested backup. Helm remediation
now retries in place instead of choosing a destructive recovery automatically.
